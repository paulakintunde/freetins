# Freetins production audit

Audit date: 24 August 2026  
Audited deployment: `https://freetins.pages.dev/`  
Repository build: Astro 5.18.2 on Cloudflare Pages  
Scope: technical performance, SEO, UX and design, content quality, security and compliance, analytics and CRO

## Executive conclusion

The new Pages build is fast, responsive, source-led, and structurally much stronger than the old site. It is not ready to be treated as the canonical production site yet.

The primary blocker is a domain migration collision. Every page on `freetins.pages.dev` declares a canonical URL on `freetins.com`, but that hostname still serves the old site. New-route canonical targets such as `https://freetins.com/codes/grow-a-garden/` permanently redirect to the old homepage. Search engines are therefore being told that the old, unrelated response is the preferred version of every new page.

There are also two verified functional failures: global search returns no results, and an inline script used by the editorial template is emitted after `</html>` and blocked by the site's own CSP. The latter creates console errors on 19 editorial pages and breaks the Little Alchemy filter.

## Priority findings

### P0: Correct the production-domain migration

Evidence:

- All 270 audited Pages documents use `https://freetins.com/...` canonical URLs.
- `https://freetins.com/` redirects to `https://www.freetins.com/`, which serves the old site with the title `Freetins - Codes for Game, Guides, and Walkthroughs.`
- `https://freetins.com/codes/grow-a-garden/` returns `301 Location: https://www.freetins.com`, losing the destination path and landing on the old homepage.
- `robots.txt`, the sitemap index, all sitemap URLs, Open Graph URLs, and JSON-LD identifiers also use `freetins.com`.
- The source of the mismatch is `site: 'https://freetins.com'` in `astro.config.mjs`.

Impact:

- Search engines receive conflicting content and redirect signals.
- New Pages content is unlikely to rank under its intended URLs.
- Many canonical targets behave like irrelevant redirects or soft 404s.
- Social previews and structured data identify a different deployment.

Proper fix:

1. Choose one final hostname, preferably `https://www.freetins.com/` or `https://freetins.com/`, and make the decision explicit.
2. Attach that hostname to the Pages deployment and stop serving the old site there.
3. Preserve old URLs with a one-to-one redirect map to the closest new URL. Do not redirect unrelated old URLs to the homepage.
4. Set Astro `site`, canonical tags, Open Graph URLs, JSON-LD IDs, robots sitemap, and sitemap URLs to the same final hostname.
5. Redirect the non-preferred custom hostname and `freetins.pages.dev` to the preferred hostname. If Pages remains a staging hostname, send `X-Robots-Tag: noindex` there.
6. Validate redirects, canonicals, sitemap entries, and Search Console before requesting a site move.

### P0: Replace the non-working search implementation

Evidence:

- `/search/`, `/search/?q=grow-a-garden`, and `/search/?q=monopoly` return byte-identical HTML.
- A browser test found zero result links and did not find the submitted query in the main content.
- The global header/drawer search exists on all 270 pages, so this is a sitewide failed task.
- JSON-LD advertises a `SearchAction` for the non-working endpoint.
- `/search/` is included in `sitemap-0.xml` while `robots.txt` disallows crawling it.

Proper fix:

1. Build a static search index at build time and filter it client-side, or use a small Pages Function if server search is genuinely required.
2. Return only published/indexable records; do not expose the 220 drafts.
3. Add useful empty, loading, keyboard, and typo states.
4. Remove `SearchAction` until the feature works.
5. Keep internal search results out of the sitemap. Use `noindex` rather than robots blocking if crawlers need to see the directive.

### P1: Fix CSP-blocked scripts and invalid editorial HTML

Evidence:

- 19 editorial responses contain an executable `<script>` after `</html>`.
- The CSP is `script-src 'self'` and correctly blocks that inline script.
- Lighthouse recorded a CSP console error and a Chrome Issues-panel finding.
- Typing `life` into the Little Alchemy filter left all 580 cards visible; the filter does not work.
- The source is the template script at the bottom of `src/components/pages/EditorialArticle.astro`.

Proper fix:

- Move the filter behavior into the existing bundled `src/scripts/site.ts` or a separately emitted same-origin module.
- Keep the strict `script-src 'self'`; do not add `unsafe-inline` as a workaround.
- Ensure every script is inside the document and run a CSP-console test on every page template.

### P1: Upgrade the vulnerable framework/toolchain deliberately

`pnpm audit --prod` reports 29 advisories: 9 high, 14 moderate, and 6 low.

The affected dependency paths include:

- Astro 5.18.2: reflected XSS and SSRF advisories.
- `@astrojs/cloudflare` 12.6.13: image-transform SSRF advisory.
- `sharp` 0.34.5: inherited libvips vulnerabilities.
- Wrangler/Miniflare transitive `undici` and `ws`: WebSocket denial-of-service, request/response handling, and information-disclosure advisories.

The static deployment and local-only image build reduce exposure to several server/tooling findings, but they do not make the dependency tree acceptable. Plan and test an Astro major upgrade that reaches at least the patched ranges reported by the audit: Astro 7.0.10, Cloudflare adapter 13.1.10, Sharp 0.35.0, `undici` 7.29.0, and `ws` 8.21.0 or later compatible versions.

### P1: Stop routing users and crawlers into placeholders

Evidence:

- 270 generated documents exist, but 220 are `noindex, nofollow` placeholders.
- The crawl found 4,345 internal links to those noindex pages.
- Prominent global destinations such as Alerts, Submit, Blog, Daily links, and many game sub-tabs are empty or disabled.
- Operational data has 0 daily links, 0 cheats, 0 values, 0 updates, 0 products, and all checker/alerts/advertising services disabled.

Proper fix:

- Do not include planned surfaces in primary navigation until they perform a useful action.
- Do not generate every game's Values, Updates, and Archive route when the collection is empty.
- Keep plans in the content system, not in public navigation. Publish a route only when it passes a content/function readiness gate.

### P1: Establish measurement before optimizing conversion

Evidence:

- No analytics signature or Cloudflare Web Analytics beacon appears in any of 270 HTML responses.
- Lighthouse network logs contain no RUM request.
- There is no custom event instrumentation in the site script.
- Alerts, code submission, and checker services are disabled; Contact is email-only.

Proper fix:

1. Enable Cloudflare Web Analytics for privacy-first pageviews and field Core Web Vitals, updating CSP for its documented beacon endpoints.
2. Cloudflare Web Analytics does not provide custom events. Add a first-party Pages Function backed by Analytics Engine, or select a consent-compatible event product, for conversion events.
3. Start with `search_submit`, `search_result_click`, `code_copy_success`, `code_copy_failure`, `source_click`, `contact_email_click`, `alert_interest`, and later `alert_subscribe_confirmed`.
4. Define funnel denominators and data retention before adding experiments.

## Pillar 1: Technical performance

### Architecture and rendering

- Astro is configured with `output: 'static'`; the site is SSG, not SSR.
- 270 HTML documents are generated at build time.
- One on-demand endpoint, `/api/checker-status.json`, is served through the Cloudflare adapter. It currently returns a valid `Unconfigured` snapshot.
- Astro `ClientRouter` provides client-side transitions over static pages.

Assessment: the architecture is appropriate for a content site. Static generation, edge delivery, and small shared JS produce fast navigation without introducing a general SSR dependency.

### Live route and server performance

The coded production crawl measured all 270 generated routes:

- 270/270 returned HTTP 200 for their generated paths.
- Median TTFB: 47 ms.
- P95 TTFB: 71 ms.
- Maximum TTFB observed: 456 ms.
- Median full HTML fetch: 50 ms.
- P95 full HTML fetch: 73 ms.
- No broken internal route was found.

Browser interaction timings:

- Home to Codes client transition: 153 ms.
- Answers to the 315 KB Little Alchemy document: 573 ms.
- No horizontal overflow at a 390 px viewport.

### Lighthouse and Core Web Vitals proxies

Home mobile:

- Performance 91, Accessibility 96, Best Practices 100, SEO 100.
- FCP 1.25 s, LCP 1.25 s, TBT 0 ms, CLS 0.
- 17 requests and about 303 KiB transferred.

Home desktop:

- Performance 90, Accessibility 96, Best Practices 100, SEO 100.
- FCP 0.38 s, LCP 0.38 s, TBT 0 ms, CLS 0.

Grow a Garden mobile:

- Performance 90, Accessibility 96, Best Practices 100, SEO 100.
- FCP 1.09 s, LCP 1.25 s, TBT 0 ms, CLS 0.

Little Alchemy mobile, the heaviest page:

- Performance 86, Accessibility 97, Best Practices 92, SEO 100.
- FCP/LCP 1.85 s, TBT 196 ms, CLS 0.
- 4,872 DOM elements and 2.4 s of main-thread work.

The captured Speed Index values were excluded from conclusions because the sandboxed headless browser did not produce visual frames until several seconds after trace FCP/LCP. Real-user monitoring is needed for field LCP, INP, and CLS.

### Caching, compression, and assets

- Cloudflare serves Brotli compression.
- Fingerprinted `/_astro/*` assets use `public, max-age=31536000, immutable`.
- HTML uses `max-age=0, must-revalidate`, appropriate for frequently changing code data.
- Shared build output is small in code: about 64 KB uncompressed CSS and 22 KB uncompressed JS.
- The generated asset folder is 71.5 MB because it contains 960 image variants: 521 WebP and 439 AVIF files.
- The homepage has four responsive-image opportunities worth about 74 KiB in Lighthouse; adding an intermediate mobile width would avoid selecting 792 px images for roughly 606 px rendered demand at device scale.
- All 81 Open Graph images are valid 1200 x 630 JPEGs. The five largest should be recompressed; the maximum is about 255 KB.

### Build and quality gates

- Fresh production build completed successfully.
- Astro typecheck completed successfully.
- Route crawl passed: 270 documents and 15,382 internal links.
- Operational data check passed: 58 games, 133 codes, and 110 verification events.
- All four unit tests passed.

### Technical defects

- The editorial inline-script/CSP defect affects 19 pages.
- The 315 KB Little Alchemy page is a large DOM and should be monitored for mobile INP after its filter is fixed.
- `/404.html` redirects to `/404/`, which returns an indexable 200 response. Unknown URLs correctly return 404, but the error template should be `noindex` and the direct 404 route should not be a normal indexable page.
- The on-demand status endpoint does not receive the static `_headers` policy. A security-header helper exists but is unused.

## Pillar 2: Search engine optimization

### Crawlability and indexability

- 50 generated responses are indexable, including the direct 404 document.
- 220 are noindex placeholders.
- The sitemap contains 49 URLs.
- `/search/` is in the sitemap but blocked by `robots.txt`.
- No internal route is broken, but 4,345 links lead to noindex placeholders.

Assessment: crawl mechanics are technically orderly, but the public route inventory is far larger than the useful inventory and sends conflicting importance signals.

### Canonicals and migration

This is the critical SEO failure described in P0. Lighthouse's SEO score of 100 only confirms that canonical tags exist; it does not validate that the targets serve equivalent content.

### Titles, descriptions, headings, and URLs

Across all 270 pages:

- 0 missing titles or descriptions.
- 0 duplicate titles.
- 0 duplicate meta descriptions.
- 0 pages with an invalid H1 count.
- Clean directory URLs and consistent trailing slashes.
- No prototype `file:///` or hash routes leaked into the build.

These are strong foundations.

### Structured data

- All JSON-LD blocks parse successfully.
- The base graph includes Organization, WebSite, and WebPage.
- Editorial pages add Article/WebPage, BreadcrumbList, author, dates, and FAQ where available.
- The base `SearchAction` must be removed until search works.
- Operational game-code pages could add page-specific breadcrumb and appropriate collection/item schema after the canonical migration is fixed.
- Article social metadata currently uses `og:type=website`; use `article` for editorial articles.

### Internal linking

- Useful published pages are well connected through hubs, breadcrumbs, related links, and game tabs.
- Planned/noindex pages are over-linked. This is both a crawl-efficiency and user-trust problem.
- Search chips all land on the same non-working search response.

### Image SEO

- No rendered image is missing an `alt` attribute.
- Responsive AVIF/WebP is used with explicit dimensions, preventing layout shift.
- Open Graph images have correct dimensions and descriptive alt text.
- Add image sitemap data only if image-search acquisition becomes a measurable channel; it is not required for the current 49-URL sitemap.

### 404s and redirects

- Unknown URLs return 404 with the custom error document.
- The error document declares `index, follow` and canonicalizes to `/404/`; use noindex.
- The custom-domain migration uses broad redirects to the old homepage. Replace them with destination-specific redirects.

## Pillar 3: User experience and design

### Strengths

- Strong, consistent visual hierarchy and branded dark/green direction.
- Responsive layout has no 390 px horizontal overflow.
- Mobile drawer opens, moves focus to Close, traps tab focus, closes with Escape, and restores state correctly.
- Skip link, semantic landmarks, breadcrumbs, one H1 per page, live copy feedback, and reduced-motion support are present.
- Buttons and code rows provide clear states. The clipboard failure path gives a usable manual-selection message.
- Client navigation is fast on normal pages.

### Functional UX failures

- Global search performs no search.
- The Little Alchemy page advertises a searchable list, but CSP blocks its filter.
- Alerts and Submit are visible global destinations but only explain that they are inactive.
- Contact topic query parameters do not prefill or change the email route.
- Status is a global unconfigured banner rather than a useful status history/service page.

### Mobile obstruction and hierarchy

On a 390 x 844 fresh session:

- Consent panel occupied 27.8% of viewport height.
- Unconfigured-checker notice occupied 20.2%.
- Together they consumed about 48% of the viewport before the user could focus on content.

Only necessary storage is active. A full sticky consent panel is disproportionate until optional processing exists. Keep transparent cookie information in Privacy, and either remove the blocking choice UI or reduce it to a compact notice until a real choice is available.

### Accessibility

- Lighthouse found no missing names, labels, alt text, or landmark failures on tested templates.
- The repeated failure is WCAG 2.2 AA text contrast.
- Ratios between 4.18:1 and 4.35:1 fail the 4.5:1 threshold for small text.
- Affected components include stat labels, footer headings, native-card labels, and the consent eyebrow using `--text-disabled: #767676` on near-black surfaces.

Increase the dark-theme disabled/tertiary token enough to pass without rounding, then rerun all templates.

### Design-system observations

- Spacing and gutters are now generous: `--page-gutter: clamp(32px, 8vw, 120px)`.
- The system is consistent, but the font stack is entirely system UI and gives the editorial brand limited distinctiveness.
- Empty-state modules are visually honest, but too many of them in navigation make the product feel unfinished.

## Pillar 4: Content and on-page quality

### Strengths

- Operational claims are derived from structured records rather than hardcoded freshness labels.
- Published game pages include source URLs, redemption steps, absolute timestamps, and explicit verification states.
- Editorial pages include reviewed dates, author links, source lists, quick answers, jump navigation, and related content.
- No title/description duplication was found.
- The heaviest reference page contains 4,948 main-content words and the complete 580-item answer set in source HTML.

### Thin and incomplete pages

- 19 indexable generated pages contain fewer than 300 main-content words; the count includes the direct 404 page.
- 26 indexable pages contain fewer than 500 words.
- Particularly weak destinations include the 53-word author page, Search, How We Verify, Guides, Games A-Z, several archive pages, and section hubs.
- The author page does not establish credentials, editorial responsibilities, correction history, or subject experience strongly enough for the site's evidence-led positioning.
- How We Verify is a cornerstone trust page but contains only a short four-step summary.

Word count is not a ranking target by itself. Each page should remain indexable only if it fully satisfies its task.

### Source and link integrity

The automated outbound-link check tested 86 unique external links:

- 73 returned success/redirect responses.
- 9 returned anti-bot or rate-limit responses and require manual browser review.
- 4 returned verified 404 responses:
  - App Store URL on `/answers/100-pics-christmas-emoji/`.
  - App Store URL on `/answers/guess-emoji-levels-1-10/`.
  - IGN source on `/cheats/lego-jurassic-world/`.
  - mGBA documentation source on `/cheats/pokemon-emerald/`.

Repair or replace these sources and add the link checker to scheduled editorial QA.

### Editorial consistency

- Contact and legal pages consistently favor honest email-only behavior.
- Email identity is inconsistent: JSON-LD and Submit use `hello@freetins.com`, while Contact, Privacy, Terms, Disclosure, and DMCA use `support@freetins.com`.
- Standardize the public address by purpose and document both only if both are monitored.
- Add an editorial review queue for stale records, dead sources, and unverified entries instead of expanding planned route count.

## Pillar 5: Security and compliance

This section is an engineering/compliance audit, not legal advice.

### Transport and platform security

- HTTP correctly redirects to HTTPS.
- TLS 1.3 with `TLS_AES_256_GCM_SHA384` and a valid Google Trust Services certificate was verified.
- CSP, frame denial, MIME sniffing protection, restrictive Permissions Policy, and strict-origin referrer policy are present on static HTML.
- No mixed-content references were found.
- No obvious committed API keys, tokens, or private keys were found.
- The site is static and has no active form-ingestion surface, substantially reducing attack area.

### Header gaps

- `Strict-Transport-Security` is absent on `freetins.pages.dev`; the old custom site currently sends HSTS. Preserve and verify HSTS when the custom domain moves, enabling it only after all covered hostnames are permanently HTTPS.
- The on-demand JSON endpoint lacks the static security headers because Pages `_headers` rules do not apply to Worker-generated responses. Use the existing header helper in the API response.
- Add `/.well-known/security.txt` with a monitored contact and expiry date.
- COOP/CORP are optional for this content site and should not be added without testing external navigation and embeds.

### CSP

- The policy is meaningfully restrictive and should remain so.
- `style-src 'unsafe-inline'` weakens style injection protection but is currently required by the emitted Astro styling approach.
- The correct response to the blocked editorial script is to externalize it, not weaken `script-src`.

### Dependency and supply-chain security

- 29 current advisories require an upgrade project.
- Add `pnpm audit --prod` to CI with an explicit severity policy.
- Pin the package manager and lockfile, which the project already does.
- Add Dependabot or Renovate with grouped Astro/Cloudflare upgrade pull requests and full build/route/Lighthouse checks.

### Cookies and privacy behavior

- The first-party consent cookie is host-only, Secure on HTTPS, SameSite=Lax, and limited to a 180-day max age.
- Session notice state remains in session storage.
- No optional analytics, advertising, alert, or form provider currently receives user data.
- The privacy page accurately states current technical behavior.

### Privacy transparency gaps

The Privacy page should be legally reviewed before forms, alerts, advertising, or analytics launch. It does not fully identify:

- The legal controller identity and address.
- Lawful bases by processing purpose.
- Specific retention periods or criteria for each data category.
- International transfer mechanism/details.
- The applicable supervisory authority and complaint route.
- Whether Cloudflare/email subprocessors act in specific regions.

Because only necessary storage is active, consent is generally not the right legal basis for those essential operations. The panel should explain necessary storage without manufacturing an optional choice.

### Children and gaming audience

The site states it is general-audience and for ages 13+, and it currently does not collect web-form or alert data. That keeps present COPPA exposure lower. Before adding email alerts, push identifiers, submissions, accounts, or advertising, complete an audience/child-privacy assessment appropriate to a Roblox-heavy site and minimize collection by default.

### Copyright and commercial compliance

- DMCA notice requirements and a copyright contact are published, with an honest note that agent registration is not asserted.
- Affiliate/sponsorship disclosure principles are published.
- No active paid placement or affiliate product record exists, so claims must be re-audited when monetization is enabled.

## Pillar 6: Analytics and conversion optimization

### Current measurement state

- No browser analytics or field performance beacon is present.
- Cloudflare may still provide account-level edge request metrics, but that cannot measure user interactions and was not available to this code audit.
- No error monitoring is configured.
- No custom events, campaign attribution, or experiment framework exists.
- Cloudflare Web Analytics currently does not log query strings or support custom events, so it cannot be the only CRO data source.

### Current conversion state

Potential goals exist in the design, but most are not operational:

- Code copy: active micro-conversion with success/failure UI, no measurement.
- Search: visible but non-functional.
- Contact: mailto-only, no click or response measurement.
- Code submission: inactive.
- Alert signup/management: inactive.
- Push: no manifest, service worker, subscription API, or notification permission flow.
- Product/affiliate click: no published product records.

There is therefore no meaningful conversion rate to optimize yet.

### Recommended measurement architecture

1. Enable Cloudflare Web Analytics for pageviews and real-user Core Web Vitals.
2. Add a first-party `/api/events` Pages Function and Analytics Engine binding for a small, allowlisted event schema, or use a consent-compatible product with custom-event support.
3. Do not send code text, email addresses, search query strings, IP addresses, or arbitrary URLs as event payloads.
4. Record server-confirmed conversions for alert subscriptions and submissions rather than only button clicks.
5. Add error and CSP-violation monitoring with sampling and retention limits.

Initial dashboard:

- Landing page sessions by content section.
- Search use, zero-result rate, and result click-through.
- Code-copy success rate by game page.
- Source-link click rate.
- Alert interest to confirmed subscription funnel once active.
- Contact intent clicks.
- LCP, INP, and CLS at the 75th percentile by page template.
- 404 rate and top missing paths.

Do not begin A/B testing until the canonical migration, search, CSP failure, and baseline measurement are fixed.

## Recommended execution order

### Stage 1: Production correctness

1. Resolve custom-domain ownership and deploy the new build on the final hostname.
2. Implement one-to-one old-to-new redirects and redirect Pages to the canonical host.
3. Fix search and remove the false SearchAction until verified.
4. Move the editorial filter into an allowed bundled script.

### Stage 2: Security and trust

1. Upgrade Astro/Cloudflare/Sharp and transitive vulnerable packages.
2. Apply security headers to the on-demand endpoint and verify HSTS on the final host.
3. Repair the four dead sources.
4. Standardize contact email identity and complete privacy/legal review.

### Stage 3: UX and content quality

1. Remove links to unpublished/noindex surfaces.
2. Reduce the two first-visit banners to one proportionate notice.
3. Fix contrast tokens.
4. Strengthen the author, verification, and hub pages based on user tasks, not target word counts.

### Stage 4: Measurement and conversion

1. Enable field performance/pageview analytics.
2. Add privacy-minimized custom event collection.
3. Build the first real conversion: alert interest to confirmed subscription, or code submission to reviewed outcome.
4. Add monitoring and only then begin iterative CRO tests.
